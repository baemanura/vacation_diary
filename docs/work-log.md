### 정한 것 — 다시 꺼내지 말 것

- **근무 주기는 코드 상수 하나로 둔다.** `DUTY_CYCLE_ANCHOR = '2026-09-19'`(일근), 이후
  일근 → 당직 → 비번 3일 주기. 서무가 화면에서 고치게 하는 안은 **실제로 주기가 어긋나는
  일이 생기면 그때 만들기로** 하고 미뤘다. 밀리면 이 한 줄만 고쳐 배포한다.
- **기준일 이전 날짜는 표시도 정원 보정도 하지 않는다.** 인사이동 전이라 편성이 달랐다.
- **일근일에 늘어나는 인원은 코드가 아니라 정원 설정에 둔다.** 출동율이 바뀌면 추가 인원도
  달라질 수 있는데 그때마다 배포를 기다릴 수 없다. 서무가 기간마다 +0~10명으로 정한다.
- **달력에는 일근만 표시하고 당직·비번은 표시하지 않는다.** 연가를 낼지 판단하는 데 필요한
  것은 "오늘 한 명 더 갈 수 있는가"뿐이고, 나머지는 달력을 읽기 어렵게만 만든다.
- **전체 관리자는 새 역할이 아니라 `role='admin'` + 표시 칸이다.** 이유는
  `database-changes.md`의 `is_owner` 항목에 적었다(RLS 정책을 읽을 수 없다는 것이 핵심).
  서무 화면에서 **숨기지 않고 보이되 잠근다** — 서무가 바뀌었을 때 정체를 알 수 없는 계정이
  하나 떠 있는 편이 더 나쁘다.
- **순번 중복은 막고 알려준다. 자동으로 맞바꾸지 않는다.** 서무가 의도한 것이 맞바꿈인지
  밀어내기인지 앱이 알 수 없고, 잘못 짐작하면 건드리지도 않은 사람의 순번이 조용히 바뀐다.
- **긴 특가·교육도 정원 한 자리를 그대로 차지한다.** 아래 점검에서 이장원 경장이 9월 한 달
  내내(교육 11일 + 특가 19일) 가능인원 2명 중 한 자리를 매일 먹고 있고, 그 때문에 9월에
  '주의'로 뜨는 날이 5일이라는 것을 확인해 사용자에게 물었다. **"지금처럼 냅둬"로 정해졌다.**
  `occupiesQuota()`는 **3개월 이상 휴직만** 예외로 둔 채 유지한다.

### 권한 경계 — 이번에 실제로 확인한 것

`is_owner`를 넣으면서 **프로필을 브라우저에서 직접 고칠 수 있는지** 처음으로 실측했다.

- **일반 대원 토큰**으로 자기 행에 `role='admin'`, `is_owner=true`, 이름 변경을 각각 PATCH →
  전부 **HTTP 200에 0건**. RLS가 조용히 막는다. **대원이 스스로 서무가 되는 길은 없다.**
- **서무 토큰**으로는 UPDATE 자체가 통과한다(행이 돌아온다). 그래서 `is_owner`는 트리거로
  막아야 했다 — 트리거가 이 칸만 원래 값으로 되돌린다.
- 검사에 쓴 임시 계정은 프로필과 auth 계정 모두 삭제했다.

> **200이 돌아왔다고 바뀐 것이 아니다.** 이 프로젝트에서 반복되는 함정이다.

### 다음에 손볼 때 알아둘 것

- **배포 확인은 폴링하지 말 것.** ~110초 기다린 뒤 **한 번만**, 브라우저 User-Agent로
  `/_next/static/chunks/*.js`를 받아 새로 넣은 문구를 `grep`한다. 이때 **그 문구가 어느
  페이지 번들에 들어가는지**를 맞춰야 한다 — `/dashboard`에서 `/admin` 전용 문구를 찾으면
  배포가 됐는데도 "아직 이전 버전"이 나온다(이번에 한 번 겪었다).
- **`last_sign_in_at`은 활동 지표가 아니다.** 세션이 유지되어 재로그인이 없으면 갱신되지
  않는다. 실제 활동은 `leave_requests.created_at`으로 본다. 이 값이 쓸모 있는 곳은 **한 번도
  쓰지 않은 사람**을 찾을 때뿐이다.
- **Supabase SQL 편집기는 긴 SQL을 잘라 넣는 일이 있다.** `CREATE TRIGGER ... EXECUTE
  FUNCTION ...`이 `EXECUTE FUN);`으로 들어가 42601이 났다. 덩어리를 나눠 실행하고, 붙여넣은
  뒤 마지막 글자가 `;`인지 확인한다. 오류가 나면 전체가 롤백되므로 중간 상태는 남지 않는다.
